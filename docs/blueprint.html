Design blueprint · school management platform

Pathshala Blueprint

An A-to-Z school management system where every section runs on the same event-and-rule engine: admissions, academics, attendance, exams, fees and accounting, HR and payroll, library, transport, hostel, inventory, communication, welfare, certificates and front office.

205 tables in 20 modules 90+ automations (system handlers, rules, cron) 36-week build plan, pilot at week 16 Defaults: BDT · Asia/Dhaka · Fri–Sat weekend · GPA 5.0 · bKash / Nagad / SSLCommerz
01 · Runtime

System architecture

One deployable API, one worker process, one Postgres. Every write the API makes also writes an event row in the same transaction; the worker turns those events into everything that happens next.

02 · Mechanism

Automation engine

Three ingredients make "every section automated" a property of the platform rather than a feature list: a transactional outbox, a rule table schools can edit, and a scheduler whose cron jobs also emit events so rules can chain.

Worked example · a guardian pays tuition with bKash

  1. The guardian app calls the payment endpoint. The API creates a pending payment and returns the bKash URL.
  2. bKash calls the IPN endpoint. The API verifies the signature, then in one transaction marks the payment successful, allocates it to the oldest open invoices, appends the student ledger entry and inserts the payment.received outbox event.
  3. The relay publishes the event. The system handler posts a balanced journal: debit bKash merchant account, credit tuition income, credit fine income, debit gateway-fee expense.
  4. The "receipt" rule queues a PDF job. Gotenberg renders the receipt template and the file is attached to the payment.
  5. The "payment thanks" rule sends a push and, if push is not delivered, an SMS in the guardian's language.
  6. The "unblock" rule sees no overdue invoice remains and re-enables the admit card for the upcoming exam.
  7. Each step is visible under Automation → Activity with its result or its retry state.
03 · Structure

Module map

Modules read each other through services and never write each other's tables. Money is the one place everything converges: five modules feed billing, and billing, payroll and purchasing feed the ledger.

04 · Data

Schema by module

Real PostgreSQL 16 DDL lives in db/schema/, one numbered file per module. Conventions: UUID keys, school_id on every tenant table with row-level security, soft deletes, frozen JSON snapshots wherever a document is issued.

07 · Choices

Stack

TypeScript end to end so the event catalogue is one shared package. A Python team could build the same schema with Django and Celery; nothing in the design depends on the framework.

LayerChoiceWhy
APINestJS modular monolith, REST + OpenAPIOne deployable with hard module boundaries; split later only if needed.
DatabasePostgreSQL 16 with RLS, btree_gist, pg_trgm, pgcryptoExclusion constraints solve timetable and room clashes in the database itself.
Data accessDrizzle ORM plus raw SQL for reportsSQL-first; the DDL stays the source of truth.
QueuesRedis 7 + BullMQNamed queues for notifications, billing, payroll, PDF, sync and reports; retries with back-off.
FilesMinIO self-hosted or S3 / R2Photos, documents and generated PDFs via pre-signed URLs.
PDFGotenbergRenders the same HTML templates schools edit for report cards, receipts, certificates.
WebNext.js 15, Tailwind, TanStack QueryAdmin, accounts and teacher desks.
MobileExpo / React Native, FCM pushGuardian, student, teacher and bus-helper apps from one codebase.
AuthJWT 15 min + refresh sessions, SMS OTP for guardians, TOTP for adminsPhone number is the guardian's identity in Bangladesh.
BIMetabase on a read-only role and the daily KPI tablePrincipal dashboards without custom code.
InfraDocker Compose on one VPS, Kubernetes past ~50 schoolsEverything is stateless except Postgres, Redis and MinIO.

Definition of done for any automation

Event or cron documented. Handler idempotent. Run visible in the activity log with a readable result. Failure notifies an admin. Integration test covers the happy path and one failure.

Biggest risks

SMS cost and delivery (push first, SMS fallback, balance alerts). Device variety (thin adapter per vendor, one resolver). Messy legacy data (import with error file, draft students until verified). Automation surprises at scale (preview mode for 48 h after a rule change, per-rule kill switch, cooldowns).
